Chained Kit Replacement with the SAS Hash Object

How to resolve a replacement chain of unknown depth in a single pass of a DATA step, why an in-memory hash is the only structure that fits this shape of problem, and what the pattern does when the input is not clean.

Source  IRT kit-derivation step of the SDTM EC validation program Status  Logic validated against a reference model; not executed under SAS here
De-identification and scope

All study identifiers are replaced by the placeholder NNNN. Library names, file paths, program headers and input dataset names have been removed or generalised. Line numbering is intentionally absent: the listings are self-contained and are referred to by step and by marker, so the document can be lifted into another program without editing references.

This note covers the kit-replacement derivation only — the split of the IRT feed, the chain walk, the collapse to one record per subject and visit, and the join back to the clinical records. It is not a general hash tutorial and not a full SDTM EC mapping specification.

1The problem the code solves

A linked list stored as rows, and the identifiers that have to come out of the far end of it.

The derivation requirement is short. ECREFID, ECLOT and BATCHNUM must carry the final kit associated with a visit, not the kit that happened to be recorded at that visit, because a kit may be replaced one or more times before or during administration. The IRT extract records both facts in the same table: the kit used, and the kit it was replaced by.

That makes the input a singly linked list. Each row is a node, kitnumrp is the pointer, and the terminal node is the one whose kitnumrp is missing. Walking a linked list requires random access to the node table from inside a loop, which is exactly what a hash object provides and what a merge does not.

1.1 Terms

VariableRole in the pattern
scn_numSubject identifier. Half of the hash key, and the join key back to SUBJID.
vis_typeVisit label. Drives the split, and is the join key back to VISIT.
kit_tydsKit type. Part of the collapse key; a visit may legitimately carry several kit types.
kit_numKit number. The second half of the hash key, and the value that is rewritten by the walk.
kitnumrp“Kit number replacement”: the kit that this kit was replaced by. Missing on a terminal kit. This is the pointer.
lot_num, btch_numLot and batch of the row's kit. Carried as hash payload so the terminal hop supplies them.
The shape of the problem

Three properties are needed at the same time: re-probe the same table with a different key inside one observation; do not require the driving table to be sorted by the lookup key; and cope with a chain depth that is not known until the data is read. A single merge or join satisfies none of the three.

2Hash essentials

The minimum that has to be understood before the code in section 3 reads as obvious.

2.1 Skeleton

if _n_ = 1 then do;                                     (1)
   declare hash h(dataset: "irt_rp");                 (2)
   h.definekey("scn_num","kit_num");                  (3)
   h.definedata("kitnumrp","lot_num","btch_num");     (4)
   h.definedone();                                    (5)
end;
...
rc = h.find();                                        (6)
  1. The guard. declare is a compile-time statement, but the object is created and the table read when the step executes. Without if _n_ = 1 the object would be rebuilt, and the table re-read, on every iteration — correct results, unacceptable cost.
  2. Declare and point at the source table. A data set name in the dataset: tag is loaded automatically; hashexp:, ordered: and duplicate: may be added here.
  3. The key: the variables that form the address. Define the key first. Key values are looked up by comparing the current values of these PDV variables.
  4. The data: the payload returned by a successful probe. A variable may be declared as both key and data; it then behaves as key for matching and as payload for the write-back.
  5. Ends the definition and triggers the load. Every name passed to definekey or definedata must already exist in the PDV at this point.
  6. The probe. Called with no arguments, it uses the PDV variables named in steps 3 and 4; a different driver can be passed with the key: tag.

2.2 The one design decision that carries the whole pattern

In this program kitnumrp is declared as data, even though it also drives the loop. That is deliberate and load-bearing. A successful find() writes the payload straight back into the PDV, so the loop control variable is silently advanced to the next link. Nothing else in the step has to re-assign it, and the terminal hop's lot_num and btch_num arrive in the same write, which is what makes ECLOT and BATCHNUM consistent with the terminal kit.

2.3 Argument tags worth knowing

TagEffect
dataset: "name"Loads the table at definedone(). Data set options such as where= and keep= may be embedded in the string.
duplicate: "replace" | "error"Default keeps the first row for a repeated key and writes nothing to the log. "replace" keeps the last; "error" makes a duplicate key fail loudly.
multidata: "yes"Allows several payloads per key, traversed with find_next. Use when one kit legitimately has more than one replacement record.
hashexp: nBucket count as a power of two; default 8 (256 buckets). Irrelevant at the scale of a replacement table.
ordered: "yes"Keeps entries in key order, which is required before iterating with a hash iterator.

2.4 Methods used, and the ones to reach for next

MethodPurpose
definekey / definedata / definedoneBuild the object. Order is fixed.
find()Look up the current key; on a hit, copy the payload into the PDV. Returns 0 on a hit.
check()Same test without copying the payload. Useful for existence tests where the old values must survive.
add() / replace() / remove()Maintain the object at run time instead of loading it from a table.
output(dataset:)Write the current contents out; the cheapest way to inspect what was actually loaded.
num_itemsAttribute, not a method: the number of entries. Put it in the log as a load check.
The return-code contract

0 means success and a non-zero value means failure — the opposite of what most people expect. Assign the return code to a variable and test it. If a method fails and its return code was not assigned, SAS writes an error to the log; if it was assigned, the failure is silent until you look. Both halves of that sentence matter: always capture rc, and always test it.

2.5 Pitfalls

SymptomCause and remedy
NOTE: Variable X is uninitialized The compiler cannot see the assignments performed by the hash, so a key or data variable that has no assignment anywhere in the step is reported. Give every such variable a length and an initial assignment (or call missing). In this program all three payload variables also arrive from the driving set, so the note does not appear — remove them from that join and it will.
Extra columns in the output data set Variables created for the hash live in the PDV and are written out with everything else. Add them to a drop unless they are intended deliverables.
Silent wrong lookup, no message A duplicate key was loaded and the first row won. Decide the rule and enforce it, or use duplicate: "error".
ERROR: Undeclared data symbol A name passed to definekey/definedata is not in the PDV. A length statement, or if 0 then set, creates it.
Every observation returns the same value The key variable is not the one being updated by the set, or the driver was passed with a literal instead of a variable. Names resolve case-insensitively, so this is almost always a wrong name, not a wrong case.

3Reading the code

Four steps, in the order they must run.

Listing 1 — split, deduplicate, walk

/* 1. split the IRT feed: visit-level rows go to irt_base, replacement rows to irt_rp */
data irt_base irt_rp;                                             (1)
     set raw.irt_kit;                                            (2)
     vis_type = upcase(vis_type);                                (3)
     if vis_type = "DISCONTINUE" then vis_type = "END OF TREATMENT";
     keep scn_num kit_tyds kit_num lot_num vis_type btch_num kitnumrp;   (4)
     if vis_type = "KIT REPLACEMENT" then output irt_rp;
     else if not missing(kit_tyds) then output irt_base;    (5)
run;

/* 2. one row per kit, so the hash key is unique by construction */
proc sort data = irt_rp nodupkey;
     by scn_num kit_num;                                        (6)
run;

/* 3. walk the replacement chain to its terminal kit */
data irt_chase;
     if _n_ = 1 then do;
          declare hash h(dataset: "irt_rp");                      (7)
          h.definekey("scn_num","kit_num");
          h.definedata("kitnumrp","lot_num","btch_num");         (8)
          h.definedone();
     end;
     set irt_base;                                              (9)

     do i = 1 to 100 while (not missing(kitnumrp));            (10)
          put "Start: "  i= scn_num= kit_num= kitnumrp=;         (11)
          kit_num = kitnumrp;                                    (12)
          put "Assign: " i= scn_num= kit_num= kitnumrp=;
          rc = h.find();                                         (13)
          put "find: "   i= scn_num= kit_num= kitnumrp= rc=;
          if rc ne 0 then do;                                      (14)
               put "CAUTION: replacement kit not found...";
               leave;
          end;
     end;
     drop i kitnumrp;                                           (15)
run;

/* 4. collapse to one reference list per subject and visit */
proc sort data = irt_chase;
     by scn_num vis_type kit_tyds kit_num;                       (16)
run;

data irt_claps;
     set irt_chase;
     by scn_num vis_type kit_tyds kit_num;
     length refid $200;                                         (17)
     retain refid;
     if first.vis_type then refid = strip(put(kit_num, best.));
     else refid = strip(refid) || ', ' || strip(put(kit_num, best.));
     if last.vis_type;                                           (18)
run;
  1. Two output data sets from one pass. The explicit output statements below mean each input row reaches at most one of them.
  2. The single IRT extract. It holds both kinds of row, distinguished by vis_type.
  3. Case normalisation before the split, so the string comparisons on the following lines are reliable.
  4. The keep list defines the PDV. Every variable the hash later needs is declared here, which is why section 2.5's first pitfall does not apply to this program.
  5. A row with no kit type is dropped: it is not a kit event and has no place in the visit-level feed. This is deliberate, and it is silent — see finding F6.
  6. Deduplication. The hash would keep the first row for a repeated key anyway, so this makes the intent explicit rather than changing the outcome — but see finding F3 for what “first” depends on.
  7. The object is declared and loaded once, from the deduplicated table.
  8. kitnumrp is payload, not just a pointer: a hit overwrites it with the next link.
  9. The driving table. Its physical order is preserved, and nothing has to be sorted by the lookup key.
  10. Two termination conditions in one statement: the while test, evaluated before every iteration including the first, and a hard budget of 100 probes.
  11. The trace. Three lines per probe, on the way in, after the pointer moves, and after the lookup. This is the right instinct; making it conditional would keep the log readable (section 5.4).
  12. The pointer moves before the probe, so the row's own kit number is replaced by the recorded replacement.
  13. The probe. On a hit the payload lands in the PDV; on a miss the payload keeps its previous values.
  14. A missing replacement row ends the walk. Note what is not done here — see finding F1.
  15. The scratch variables leave the data set. kitnumrp is dropped because the assignment is now carried by kit_num.
  16. Sort order decides both the grouping and the order inside refid: kit type, then kit number.
  17. The accumulator. Built only for the groups that actually reach this step.
  18. last.vis_type is what turns a visit's several kit rows into a single output row, carrying the reference list plus the lot and batch of the last row in sort order.

Trace 1 — what one three-link walk actually looks like

These are the values the three put statements write for a single base row, in order. They are worth reading once, because they show that the loop control variable is the hash payload itself.

iStart — driver as readAssign — pointer movedfind — payload written
1kit_num 1001, kitnumrp 1002kit_num = 1002kitnumrp → 1003, rc = 0
2kit_num 1002, kitnumrp 1003kit_num = 1003kitnumrp → 1004, rc = 0
3kit_num 1003, kitnumrp 1004kit_num = 1004kitnumrp → missing, rc = 0

After iteration 3 the while test fails, the loop exits, and the row is left with kit_num = 1004, lot_num and btch_num from the terminal record. Three probes for a three-link chain, and the entry point was the pointer on the base row, not the base row's own kit number.

Listing 2 — back to the clinical records

proc sql;

     ...
run;
  1. A left join keyed on subject and visit. Unmatched visits survive with missing kit information, and nothing in the log says so.
  2. The three identifiers are taken straight from the collapsed record. Because the collapse kept one row per visit, ECREFID and ECLOT do not have the same cardinality — see finding F4.

4Why a hash, and not a merge

The comparison that decides the design, against the four properties this problem actually needs.

Approach Re-probe the same table from inside one observation Needs the driving table sorted by the lookup key Unknown chain depth, single pass
merge / set with by No — one positional match per observation Yes — both inputs must be sorted by the same keys No — one hop per merge, so depth must be known
proc sql self-join No No No — one hop per join, and SAS SQL has no recursive CTE
Format or put() lookup No — the value is fixed when the format is built No No — single hop, and the format cannot be updated at run time
set with key= (index) Yes No Yes — but every probe needs the index and costs more
Hash object Yes No Yes
The decisive argument

The walk is a pointer chase of unknown length. The number of hops is a property of the data, not of the program, so no fixed number of merges or joins can express it: a merge-based solution would have to be a macro loop that keeps joining until nothing changes, re-scanning the whole table on each pass and re-sorting the driving data by the lookup key every time — which would also destroy the subject-and-visit order that the rest of the program depends on. The hash object is the only structure that lets a DATA step ask a question of a lookup table from inside its own loop, which is precisely what a linked list requires.

Two secondary arguments point the same way. First, sorting: the visit-level feed's natural order is by subject and visit, and the downstream collapse depends on it; a merge would impose a different sort and a second re-sort afterwards. Second, cost: the replacement table is small and is read thousands of times, which is the case a hash is built for — the whole table sits in memory and each probe is a lookup rather than a scan.

When a merge is still the better tool. If the identifier needs only one hop — a single m:1 enrichment from a small reference table — a merge or a plain left join is shorter, easier to review, and easier for a second programmer to check. The hash earns its complexity only when the lookup has to happen repeatedly, with a key that changes during the observation.

One sizing rule applies either way: keep the small side in the hash. Loading the visit-level feed would make memory grow with the study, while the replacement table grows with the number of replacements.

5Robustness under imperfect input

Sixteen synthetic scenarios, the behaviours they expose, and the guardrails that close them.

How this was verified

SAS is not available in the environment where this note was written, so the program has not been executed by SAS. The chain logic was therefore re-implemented as an executable reference model — control flow, PDV persistence across loop iterations, hit-and-miss semantics of find(), the 100-probe budget, the collapse, and the join — and run against synthetic data. Every result quoted below is an executed observation of that model, and the expected values in the harness of section 5.5 are the ones it produced, not values written by hand.

The distinction matters for one class of claim: anything that depends on how a specific SAS release reacts (for example loading a zero-row table into a hash object) is marked as unverified in the scenario table. The control-flow findings — dangling references, cycles, duplicate resolution, truncation — follow from documented semantics and are reproduced by execution.

If a release objects to an empty load, the scenario will say so in the log — and that is itself worth recording.

5.2 What the walk gets right

  • Chain depth is genuinely open. One, three, eight and eleven hops all resolve, and the loop makes no assumption about how many links there are.
  • The composite key is necessary, not decorative. S11 gives two subjects the same kit number with different replacements; a key on kit_num alone would have merged them.
  • Input order of the driving table does not matter. The visit-level feed is streamed in whatever order it arrives, and no sort by the lookup key is needed.
  • Case and one known alias are handled before the split, so both the classification and the join back use normalised labels.
  • Cost is flat in chain depth. S15 walks 60,000 replacement rows and 20,000 visits with no budget exhaustion and no missing replacement.

5.3 Findings

F1  A dangling pointer leaves the kit and its lot out of step

kit_num = kitnumrp; runs before the probe, and a failed probe writes nothing back. So when a replacement kit is absent from the table, the kit number still moves while lot_num and btch_num keep the values of the kit that was replaced. S05 ends with kit 9001 and lot LOT-A, a pair that belongs to no row in the data. An ECREFID/ECLOT cross-check will not reconcile it, and nothing in the output marks the row as suspect.

Guardrail. On rc ne 0, decide the intended outcome explicitly: either restore the previous kit together with its lot and batch, or blank all three and flag the row. Do not leave the split state in place.

F2  A cycle or an over-long chain terminates silently

The 100-probe budget does stop the loop, so the program cannot hang. It also produces no diagnostic: S07 and S08 each run exactly 100 probes, exit, and leave a well-formed but wrong kit number, and the only trace is 300 lines of put output. Cyclic replacement data is not hypothetical — it is what a double-entered or partially corrected extract looks like.

Guardrail. After the loop, test the pointer rather than the loop index: missing(kitnumrp) is true exactly when the walk landed on a terminal record. In every scenario above that test separated the resolved rows from the two failures without ambiguity.

F3  Which duplicate survives is decided by row order, not by a rule

S14 gives one kit two conflicting replacement rows. Swapping their order in the input flips the resolved terminal kit from 1003 to 1004, silently, with the same data. The deduplication is not what decides this: the hash keeps the first row for a repeated key by default and writes nothing to the log, and nodupkey keeps the first row of the sort group, so the two agree with each other and both follow physical order.

That agreement is documented and, for a Base SAS input, dependable: the sort is stable and the first observation written is the first kept. It stops being dependable if the extract is ever read from a source that does not present rows in a predictable order — an in-database read or a host sort — where the retained row is explicitly not well defined.

Guardrail. Make the rule explicit in the code instead of inheriting it from row order: sort by a superseding column (replacement date or sequence) before nodupkey, or declare the object with duplicate: "error" so that a duplicate key fails loudly on load.

F4  ECREFID and ECLOT do not have the same cardinality, and the order is not the administration order

The collapse emits one row per subject and visit. refid concatenates every kit found for that visit, while ECLOT and BATCHNUM come from the single last.vis_type row. On the 80-kit stress case the reference list describes 80 kits while the lot and batch belong to exactly one of them. The ordering inside the list comes from the sort key — kit type, then kit number — so it is grouped by kit type, not by the sequence in which kits were administered.

This is a specification question rather than a bug, but it is the kind that survives to a review table: a reviewer comparing ECREFID with ECLOT sees a one-to-many relationship that the specification may not have intended.

Guardrail. Write the intended ordering and cardinality into the specification, and if a one-to-one mapping is expected, emit one row per kit instead of collapsing.

F5  The reference list is truncated at 200 characters, mid-number

length refid $200 cuts the accumulated string without warning. On the 80-kit case the result is exactly 200 characters long and ends with a fragment of a kit number, not a complete one. The capacity follows from the separator and the width of the number: 40 whole entries for 3-digit kit numbers, 33 for 4-digit, 28 for 5-digit and 25 for 6-digit, after which a partial number remains in the string.

Guardrail. Size refid from the maximum number of kits a single visit can plausibly carry, and add a self-check next to the concatenation: if length(refid) ge 200 then put "WARNING: refid truncated" scn_num= vis_type=;.

F6  The visit key is normalised differently on the two sides, and the join fails quietly

The IRT side maps DISCONTINUE by exact equality; the clinical side derives its visit from the CRF folder name and maps anything containing the substring DISCONT. The two agree on DISCONTINUE and on END OF TREATMENT, but not on a value such as DISCONTINUED, which scenario S16 exercises: the clinical side folds it into END OF TREATMENT, the IRT side leaves it alone, and the left join then matches nothing. The symptom is a blank ECREFID on those visits and no message anywhere — a left join reports nothing, and the visit simply looks as though no kit was recorded.

Both halves of the mapping are one-line fixes. The risk is structural: as long as the same visit vocabulary is maintained in two places, the two can drift again.

Guardrail. Route both sides through one shared mapping so a single edit changes both, and count the unmatched left joins in QC rather than relying on the log to say something.

5.4 Hardened chain step

The changes are additive: the resolution itself is untouched, and a status column is added so that the three outcomes can be counted in a QC step instead of being read out of the log.

data irt_chase;
     if _n_ = 1 then do;
          declare hash h(dataset: "irt_rp", duplicate: "error");   /* F3: duplicates fail loudly */
          h.definekey("scn_num","kit_num");
          h.definedata("kitnumrp","lot_num","btch_num");
          h.definedone();
     end;
     set irt_base;

     length chain_status $10;
     prev_kit = kit_num;                                           /* F1: remember where we started */
     chain_status = '';

     do i = 1 to 100 while (not missing(kitnumrp));
          kit_num = kitnumrp;
          rc = h.find();
          if rc ne 0 then do;
               chain_status = 'DANGLING';
               kit_num = prev_kit;                                 /* keep kit, lot and batch together */
               leave;
          end;
          prev_kit = kit_num;
     end;

     /* F2: after the loop the pointer is missing only on a terminal record */
     if chain_status = '' then
        chain_status = ifc(missing(kitnumrp), 'RESOLVED', 'UNRESOLVED');

     if chain_status ne 'RESOLVED' then
        put "WARNING: kit chain " chain_status= scn_num= vis_type= kit_tyds= kit_num=;  /* F2/F6 */

     drop i rc prev_kit;                                         /* keep kitnumrp for the status test */
run;

chain_status is deliberately kept in the data set: a single proc freq over it replaces grepping the log, and UNRESOLVED or DANGLING can become an edit check. The put trace of the original is reduced to one conditional line per problem row — the same information, at a hundredth of the volume.

5.5 Verification harness

Self-contained: it builds every scenario from the matrix above, walks it, and compares the outcome against the expected values produced by the reference model. Run it once when adopting the pattern, and again after any change to the split, the key or the collapse.

/* ---- the walk, wrapped so it can be reused per scenario ---- */
%macro chase(indata=, outdata=);
  data &outdata.;
     length chain_status $10;
     if _n_ = 1 then do;
        declare hash h(dataset: "work.irt_rp");
        h.definekey("scn_num","kit_num");
        h.definedata("kitnumrp","lot_num","btch_num");
        h.definedone();
     end;
     set &indata.;
     chain_status = '';
     do i = 1 to 100 while (not missing(kitnumrp));
        kit_num = kitnumrp;
        rc = h.find();
        if rc ne 0 then do; chain_status = 'DANGLING'; leave; end;
     end;
     if chain_status = '' then
        chain_status = ifc(missing(kitnumrp), 'RESOLVED', 'UNRESOLVED');
     drop i kitnumrp rc;
  run;
%mend chase;

/* ---- one scenario runner ---- */
%macro runone(name);
  data work.irt_base work.irt_rp;
     set work.raw_kit(where=(scenario="&name."));
     vis_type = upcase(vis_type);
     if vis_type = "DISCONTINUE" then vis_type = "END OF TREATMENT";
     keep rowid scn_num kit_tyds kit_num lot_num vis_type btch_num kitnumrp;
     if vis_type = "KIT REPLACEMENT" then output work.irt_rp;
     else if not missing(kit_tyds) then output work.irt_base;
  run;
  proc sort data=work.irt_rp nodupkey; by scn_num kit_num; run;
  %chase(indata=work.irt_base, outdata=work.chase_out);
  data work.got;
     length scenario $4;
     set work.chase_out;
     scenario = "&name.";
     keep scenario rowid kit_num lot_num btch_num chain_status;
  run;
  proc append base=work.all_got data=work.got force; run;
%mend runone;

6Reuse checklist

What to change, and what to check before the pattern goes into another program.

  • Parameterise the input and the join key. The IRT table name, the subject variable and the visit variable are the only study-specific parts. Keep them in one place, and route the visit mapping used here and the one used on the clinical side through the same code.
  • Confirm the key types match. A numeric key on one side and a character key on the other gives a walk that probes with the wrong values and finds nothing. This is the failure mode most likely to reach production unnoticed, because a miss is a normal outcome of the loop.
  • Decide the duplicate rule before the first run. If two rows can describe the same kit, encode the rule in a sort column, or use duplicate: "error". Do not inherit row order.
  • Size refid from the data, not from habit. Establish the maximum number of kits a single visit can carry, multiply by the width of a kit number plus two, and add a self-check.
  • Keep a status column and count it. chain_status turns three log-only outcomes into something a QC step can fail on.
  • Keep the diagnostic under a switch. The three put statements per probe are invaluable while bedding in a new feed and unreadable once the feed is large; gate them on a macro variable.
  • Drop the scratch variables. The hash payload and the pointer live in the PDV and are written out with everything else unless they are dropped deliberately.
  • Re-run the harness after any change to the split, the key definition or the collapse. The expected values are cheap to maintain and the scenarios are the ones that actually break.
