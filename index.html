Chained Kit Replacement with the SAS Hash Object

How to resolve a replacement chain of unknown depth in a single pass of a DATA step, why an in-memory hash is the only structure that fits this shape of problem, and what the pattern does when the input is not clean.

Source  IRT kit-derivation step of the SDTM EC validation program Status  Ships a self-contained Base SAS check — 17 scenarios, one verdict per assertion
De-identification and scope

All study identifiers are replaced by the placeholder NNNN. Library names, file paths, program headers and input dataset names have been removed or generalised. Line numbering is intentionally absent: the listings are self-contained and are referred to by step and by marker, so the document can be lifted into another program without editing references.

The check that accompanies the note is synthetic in the same way: it reads no study data.

This note covers the kit-replacement derivation only — the split of the IRT feed, the chain walk, the collapse to one record per subject and visit, and the join back to the clinical records. It is not a general hash tutorial and not a full SDTM EC mapping specification.

1The problem the code solves

A linked list stored as rows, and the identifiers that have to come out of the far end of it.

The derivation requirement is short. ECREFID, ECLOT and BATCHNUM must carry the final kit associated with a visit, not the kit that happened to be recorded at that visit, because a kit may be replaced one or more times before or during administration. The IRT extract records both facts in the same table: the kit used, and the kit it was replaced by.

That makes the input a singly linked list. Each row is a node, kitnumrp is the pointer, and the terminal node is the one whose kitnumrp is missing. Walking a linked list requires random access to the node table from inside a loop, which is exactly what a hash object provides and what a merge does not.

1.1 Terms

VariableRole in the pattern
scn_numSubject identifier. Half of the hash key, and the join key back to SUBJID.
vis_typeVisit label. Drives the split, and is the join key back to VISIT.
kit_tydsKit type. Part of the collapse key; a visit may legitimately carry several kit types.
kit_numKit number. The second half of the hash key, and the value that is rewritten by the walk.
kitnumrp“Kit number replacement”: the kit that this kit was replaced by. Missing on a terminal kit. This is the pointer.
lot_num, btch_numLot and batch of the row's kit. Carried as hash payload so the terminal hop supplies them.
The shape of the problem

Three properties are needed at the same time: re-probe the same table with a different key inside one observation; do not require the driving table to be sorted by the lookup key; and cope with a chain depth that is not known until the data is read. A single merge or join satisfies none of the three.

2Hash essentials

The minimum that has to be understood before the code in section 3 reads as obvious.

2.1 Skeleton

if _n_ = 1 then do;                                     (1)
   declare hash h(dataset: "irt_rp",
                                             duplicate: "error");          (2)
   h.definekey("scn_num","kit_num");                  (3)
   h.definedata("kitnumrp","lot_num","btch_num");     (4)
   h.definedone();                                    (5)
end;
...
rc = h.find();                                        (6)
  1. The guard. declare is a compile-time statement, but the object is created and the table read when the step executes. Without if _n_ = 1 the object would be rebuilt, and the table re-read, on every iteration — correct results, unacceptable cost.
  2. Declare and point at the source table. A data set name in the dataset: tag is loaded automatically, and hashexp: and ordered: may be added here as well. duplicate: belongs here too: it is the rule the load applies to a repeated key, and Listing 3 depends on it.
  3. The key: the variables that form the address. Define the key first. Key values are looked up by comparing the current values of these PDV variables.
  4. The data: the payload returned by a successful probe. A variable may be declared as both key and data; it then behaves as key for matching and as payload for the write-back.
  5. Ends the definition and triggers the load. Every name passed to definekey or definedata must already exist in the PDV at this point.
  6. The probe. Called with no arguments, it uses the PDV variables named in steps 3 and 4; a different driver can be passed with the key: tag.

2.2 The one design decision that carries the whole pattern

In this program kitnumrp is declared as data, even though it also drives the loop. That is deliberate and load-bearing. A successful find() writes the payload straight back into the PDV, so the loop control variable is silently advanced to the next link. Nothing else in the step has to re-assign it, and the terminal hop's lot_num and btch_num arrive in the same write, which is what makes ECLOT and BATCHNUM consistent with the terminal kit.

2.3 Argument tags worth knowing

TagEffect
dataset: "name"Loads the table at definedone(). Data set options such as where= and keep= may be embedded in the string.
duplicate: "replace" | "error"Default keeps the first row for a repeated key and writes nothing to the log. "replace" keeps the last; "error" makes a duplicate key fail loudly.
multidata: "yes"Allows several payloads per key, traversed with find_next. Use when one kit legitimately has more than one replacement record.
hashexp: nBucket count as a power of two; default 8 (256 buckets). Irrelevant at the scale of a replacement table.
ordered: "yes"Keeps entries in key order, which is required before iterating with a hash iterator.

2.4 Methods used, and the ones to reach for next

MethodPurpose
definekey / definedata / definedoneBuild the object. Order is fixed.
find()Look up the current key; on a hit, copy the payload into the PDV. Returns 0 on a hit.
check()Same test without copying the payload. Useful for existence tests where the old values must survive.
add() / replace() / remove()Maintain the object at run time instead of loading it from a table.
output(dataset:)Write the current contents out; the cheapest way to inspect what was actually loaded.
num_itemsAttribute, not a method: the number of entries. Put it in the log as a load check.
The return-code contract

0 means success and a non-zero value means failure — the opposite of what most people expect. Assign the return code to a variable and test it. If a method fails and its return code was not assigned, SAS writes an error to the log; if it was assigned, the failure is silent until you look. Both halves of that sentence matter: always capture rc, and always test it.

2.5 Pitfalls

SymptomCause and remedy
NOTE: Variable X is uninitialized The compiler cannot see the assignments performed by the hash, so a key or data variable that has no assignment anywhere in the step is reported. Give every such variable a length and an initial assignment (or call missing). In this program all three payload variables also arrive from the driving set, so the note does not appear — remove them from that join and it will.
Extra columns in the output data set Variables created for the hash live in the PDV and are written out with everything else. Add them to a drop unless they are intended deliverables.
Silent wrong lookup, no message A duplicate key was loaded and the first row won. Decide the rule and enforce it, or use duplicate: "error".
ERROR: Undeclared data symbol A name passed to definekey/definedata is not in the PDV. A length statement, or if 0 then set, creates it.
Every observation returns the same value The key variable is not the one being updated by the set, or the driver was passed with a literal instead of a variable. Names resolve case-insensitively, so this is almost always a wrong name, not a wrong case.

3Reading the code

Five steps in the order they run: split the feed, reduce it to one row per kit, walk the chain, collapse the result back to one record per visit, and join it to the clinical records.

Listing 1 — split the feed

data irt_base irt_rp;                                        (1)
     set raw.irt_kit;                                        (2)
     vis_type = upcase(vis_type);
     if vis_type = "DISCONTINUE" then vis_type = "END OF TREATMENT";
     keep scn_num kit_tyds kit_num lot_num vis_type btch_num kitnumrp;
     if vis_type = "KIT REPLACEMENT" then output irt_rp;
     else if not missing(kit_tyds) then output irt_base;     (3)
run;
  1. Two output data sets from one pass. The explicit output statements below mean each input row reaches at most one of them.
  2. The single IRT extract. It holds both kinds of row, distinguished by vis_type.
  3. Case normalisation before the split, so the comparisons on the two lines above it are reliable. A row with no kit type is dropped here — it is not a kit event and has no place in the visit-level feed (scenario S13). This is also the first half of the visit mapping; see F6.

Listing 2 — one row per kit, key and payload together

/* One row per kit for hash load. The BY list carries the payload as well, so a
   conflicting pair of replacement rows survives this step, and the load -- which
   is declared duplicate:"error" below -- refuses it instead of silently keeping
   the first row it happened to read. */
proc sort data = irt_rp nodupkey;
     by scn_num kit_num kitnumrp lot_num btch_num;           (4)
run;
  1. The deduplication and the guardrail are one decision, not two. The by list is the hash key (scn_num, kit_num) plus the hash payload (kitnumrp, lot_num, btch_num), so this step collapses only rows that are identical on all five fields — one event recorded twice — and leaves a genuine conflict for the load to refuse. §5.4 works through both cases.

Listing 3 — walk the replacement chain to its terminal kit

data irt_chase;
     if _n_ = 1 then do;
          declare hash h(dataset: "irt_rp", duplicate: "error");   /* F3 */   (5)
          h.definekey("scn_num","kit_num");
          h.definedata("kitnumrp","lot_num","btch_num");                     (6)
          h.definedone();
     end;
     set irt_base;                                                           (7)

     length chain_status $10;                                                (8)
     prev_kit = kit_num;                                            /* F1 */
     chain_status = '';

     do i = 1 to 100 while (not missing(kitnumrp));                          (9)
          kit_num = kitnumrp;                                                (10)
          rc = h.find();                                                     (11)
          if rc ne 0 then do;
               chain_status = 'DANGLING';
               kit_num = prev_kit;                                  /* F1 */
               leave;
          end;
          prev_kit = kit_num;
     end;

     if chain_status = '' then                                       /* F2 */
        chain_status = ifc(missing(kitnumrp), 'RESOLVED', 'UNRESOLVED');

     if chain_status ne 'RESOLVED' then
        put "WARNING: kit chain " chain_status= scn_num= vis_type= kit_tyds= kit_num=;

     drop i rc prev_kit;
run;
  1. The object is declared and loaded once, from the deduplicated table, with the duplicate rule attached.
  2. kitnumrp is payload, not just a pointer: a hit overwrites it with the next link, so the loop control variable is advanced by the lookup itself, and the terminal hop's lot_num and btch_num arrive in the same write.
  3. The driving table. Its physical order is preserved, and nothing has to be sorted by the lookup key.
  4. The status column. It is kept in the output data set, so proc freq over it replaces grepping the log, and a QC step can fail on it.
  5. Two termination conditions in one statement: the while test, evaluated before every iteration including the first, and a hard budget of 100 probes.
  6. The pointer moves before the probe, so the row's own kit number is replaced by the recorded replacement.
  7. The probe. On a hit the payload lands in the PDV; on a miss nothing is written back, which is why the miss branch has to restore the previous kit itself.

Trace 1 — what one three-link walk does to the PDV

The table follows a single visit-level row whose kit 1001 was replaced by 1002, then 1003, then 1004. It is a reading of the listing above, not a log extract: the step writes a line to the log only when a chain fails to resolve.

iBefore the probeAfter find()Payload in the PDV
1kit_num = 1002rc = 0kitnumrp → 1003, lot LOT-B, batch B02
2kit_num = 1003rc = 0kitnumrp → 1004, lot LOT-C, batch B03
3kit_num = 1004rc = 0kitnumrp → missing, lot LOT-D, batch B04

After iteration 3 the while test fails, the loop exits, and the row is left with kit_num = 1004 and the lot and batch of kit 1004, because all three were written back by the same probe. Three probes for a three-link chain, and the first probe was aimed at the pointer on the base row, not at the base row's own kit number.

Listing 4 — collapse to one record per visit

proc sort data = irt_chase;
     by scn_num vis_type kit_tyds kit_num;                   (12)
run;

data irt_claps;
     set irt_chase;
     by scn_num vis_type kit_tyds kit_num;
     length refid $200;                                      (13)
     retain refid;
     if first.vis_type then refid = strip(put(kit_num, best.));
     else refid = strip(refid) || ', ' || strip(put(kit_num, best.));
     if last.vis_type;                                       (14)
run;
  1. Sort order decides both the grouping and the order inside refid: kit type, then kit number. It is not the order in which the kits were administered — see F4.
  2. The accumulator, sized at 200 characters. Nothing warns when the list outgrows it — see F5.
  3. last.vis_type turns a visit's several kit rows into one output row: the reference list, plus the lot and batch of the last row in sort order.

Listing 5 — back to the clinical records

proc sql;
     create table ec_ext as
     select a.*, c.kit_tyds, c.kit_num, c.refid, c.lot_num, c.BTCH_NUM, c.vis_type
     from ec_dy as a left join irt_claps as c
     on a.subjid = c.scn_num and a.visit = c.vis_type;       (15)
quit;
data ec_asgn;
     length domain $2 eclnkid $20 eclot ecrefid $200;
     set ec_ext;
     domain = 'EC';
     if ecstdtc ne '' then
     eclnkid = strip(compress(ecstdtc,"-:"))||'-'||upcase(substr(ectrt,1,1));
     else eclnkid = '';
     ecrefid = strip(refid);                                 (16)
     eclot   = strip(lot_num);
     BATCHNUM = strip(BTCH_NUM);
     if not missing(ecstdtc) then epoch = 'TREATMENT';
run;
  1. A left join keyed on subject and visit. The join key is numeric on one side and character on the other in some extracts; a type mismatch makes the join miss silently. A visit that matches nothing survives with missing kit information, and nothing in the log says so — see F6.
  2. The three identifiers are taken straight from the collapsed record. ECREFID lists every kit the visit resolved to, while ECLOT and BATCHNUM come from the one row the collapse kept, so the three do not have the same cardinality — see F4.

4Why a hash, and not a merge

The comparison that decides the design, against the four properties this problem actually needs.

Approach Re-probe the same table from inside one observation Needs the driving table sorted by the lookup key Unknown chain depth, single pass
merge / set with by No — one positional match per observation Yes — both inputs must be sorted by the same keys No — one hop per merge, so depth must be known
proc sql self-join No No No — one hop per join, and SAS SQL has no recursive CTE
Format or put() lookup No — the value is fixed when the format is built No No — single hop, and the format cannot be updated at run time
set with key= (index) Yes No Yes — but every probe needs the index and costs more
Hash object Yes No Yes
The decisive argument

The walk is a pointer chase of unknown length. The number of hops is a property of the data, not of the program, so no fixed number of merges or joins can express it: a merge-based solution would have to be a macro loop that keeps joining until nothing changes, re-scanning the whole table on each pass and re-sorting the driving data by the lookup key every time — which would also destroy the subject-and-visit order that the rest of the program depends on. The hash object is the only structure that lets a DATA step ask a question of a lookup table from inside its own loop, which is precisely what a linked list requires.

Two secondary arguments point the same way. First, sorting: the visit-level feed's natural order is by subject and visit, and the downstream collapse depends on it; a merge would impose a different sort and a second re-sort afterwards. Second, cost: the replacement table is small and is read thousands of times, which is the case a hash is built for — the whole table sits in memory and each probe is a lookup rather than a scan.

When a merge is still the better tool. If the identifier needs only one hop — a single m:1 enrichment from a small reference table — a merge or a plain left join is shorter, easier to review, and easier for a second programmer to check. The hash earns its complexity only when the lookup has to happen repeatedly, with a key that changes during the observation.

One sizing rule applies either way: keep the small side in the hash. Loading the visit-level feed would make memory grow with the study, while the replacement table grows with the number of replacements.

5Design and correctness

What the step guarantees, what it does when the input is not clean, and which of its parts carry that weight.

How this is argued, and how it is checked

The sections below read the step for what it must do with each shape of input, and say which line does it. The instrument is kit_chain_check.sas, which ships with this note: one self-contained Base SAS program that builds every scenario in §5.2 as dummy data, runs the four chain steps over it, and asserts the kit, the lot, the batch, the status and the number of probes for every visit-level row. It needs no study macros and no external libraries, and it prints one verdict per assertion.

There was no SAS session in the environment where this note was written, so the expected results in §5.2 are requirements rather than observations: they say what the code must produce. They were cross-checked against a dependency-free emulation of the same step, kept beside this note in reference-model/, and the verifier is what turns them into SAS-produced evidence in the log of whoever runs it. §7.5 lists the three behaviours that only a real session can settle.

5.1 What the step guarantees

GuaranteeWhere it comes from
G1  The hash is loaded with one row per key, or the step does not run. The by list of the deduplication carries the key and the payload, so a conflict survives it (Listing 2); the object is declared duplicate: "error", so the conflict stops the load (Listing 3, marker 5).
G2  A probe that hits advances the kit, the lot and the batch together; a probe that misses changes none of them. All three are declared as hash payload, so find() writes them back in one go; the miss branch restores the previous kit instead of leaving the pointer moved.
G3  The walk cannot hang, and it cannot stop early in silence. The budget of 100 probes bounds the loop; chain_status is computed after the loop from the pointer, which is missing only when the walk reached a terminal record.
G4  Every unresolved row is labelled and logged; no resolved row is. chain_status is kept in the output, and the put is gated on it. Both directions are asserted by the check, so a later edit cannot quietly turn the diagnostic off or leave it on for clean data.

5.3 When the chain does not resolve

Two shapes of bad input reach the walk, and they fail differently. Both are worth knowing, because neither is visible in the output unless the status column is read.

F1  A dangling pointer would leave the kit and its lot out of step

kit_num = kitnumrp; runs before the probe, and a miss writes nothing back. Without the miss branch the row would leave with a kit number taken from the replacement record and a lot and batch taken from the row it replaced — a combination that exists in no record, that no ECREFID / ECLOT cross-check can reconcile, and that nothing in the output marks as suspect. S05, S06 and S10 are that case, S10 with an empty lookup table.

How the step handles it. prev_kit holds the kit the last successful probe landed on. On a miss the kit is restored to it, so all three fields still describe one physical kit — the best available answer — and the row carries DANGLING. The verifier asserts the restored triple for S05, S06 and S10, which is what makes the restore a rule rather than a hope.

F2  A cycle or an over-long chain terminates, but on a well-formed wrong number

The budget of 100 probes stops the loop, so the program cannot hang. It produces no diagnostic of its own: S07 and S08 each make exactly 100 probes and leave a kit number that looks like any other. Cyclic replacement data is not hypothetical — it is what a double-entered or partially corrected extract looks like.

How the step handles it. After the loop the pointer is tested, not the loop index: missing(kitnumrp) is true exactly when the walk landed on a terminal record, so UNRESOLVED means the budget ran out. The number 100 decides only how long a cyclic chain takes to give up; a real chain is a handful of links (S04 walks 8, S15 walks 11), so the budget never decides an answer. The verifier asserts both cyclic cases and the probe count of 100, which is what separates "exhausted the budget" from "stopped early" in the evidence rather than in the prose.

5.4 The duplicate rule, and the deduplication in front of it

The question this section answers: the step already sorts the replacement rows with nodupkey, so is duplicate: "error" doing anything — or is the sorting the reason the load errors out?

Neither. The two statements are one decision, and the by list is where it is made. That list is the hash key plus the hash payload, so the step collapses exactly the rows that are identical on all five fields and nothing else:

CaseRows entering the sortKeys reaching the loadOutcome
S17 — two rows agree 3, of which two are byte-identical 2 The identical pair is one event recorded twice and collapses. The load proceeds; the answer is 1003 / LOT-C / B03.
S14 — two rows disagree 4, of which two claim the same kit with different replacements 4 The conflict survives the sort on purpose, and the load refuses it: ERROR: Duplicate key (101, 1002). The step stops and no output data set is produced.

So the sort does not raise the error and does not suppress the rule either: it is what gives the rule something to catch. The declaration alone would be inert, and the measurement is blunt about it — run the same four S14 rows through a by list of the key alone and they load as three keys, no duplicate ever reaches the load, and which of the two conflicting replacements wins is decided by physical order. The same data then answers 1003 / LOT-T3 / BT3 or 1004 / LOT-T4 / BT4 depending on the order the rows happen to arrive in; the emulation beside this note shows both answers from the same fixture.

What to protect

The by list of the deduplication must contain the key and every payload field the hash carries. Add a field to definedata and the same field has to be added to the by list, or a conflict on it becomes invisible again. A by list that already makes the key unique makes the declaration decorative — and the failure is silent, which is the whole reason this is written down.

One consequence is worth stating to a reviewer rather than discovering in production: a conflict is a hard stop. The DATA step ends, no data set is produced, and the job fails. That is the intended severity — an unresolved conflict must not reach a submission — but if the team prefers to see the offending rows instead, the alternative is to detect the conflict before the load and write it to a review data set, and then there is nothing left for duplicate: "error" to do.

The verifier asserts all of it except the refusal itself: the row counts entering and leaving the deduplication under both by lists, and the fact that S17 still collapses. The refusal is one log line away, in the block §7.4 describes.

5.5 What the step gets right

  • Chain depth is genuinely open. One, three, eight and eleven hops all resolve, and the loop assumes nothing about how many links there are.
  • The composite key is necessary, not decorative. S11 gives two subjects the same kit number with different replacements; a key on kit_num alone would have merged them.
  • Input order of the driving table does not matter. The visit-level feed is streamed in whatever order it arrives, and no sort by the lookup key is needed.
  • Case and one known alias are handled before the split, so both the classification and the join back use normalised labels.
  • Cost is flat in chain depth. S15 walks 20,000 visits past a 240,000-entry table at 11 probes each, with no budget exhaustion and no unresolved chain.
  • Every non-RESOLVED row carries both a status column and a log line, and no resolved row carries either.

5.6 Defects this step does not fix

Three findings are about the pipeline rather than the walk. They are recorded here because they are the same class of failure — an answer that is well formed and wrong, with nothing in the log — and because the step next to them looks trustworthy.

F4  ECREFID and ECLOT do not have the same cardinality, and the order is not the administration order

The collapse emits one row per subject and visit. refid concatenates every kit the visit resolved to, while ECLOT and BATCHNUM come from the single last.vis_type row. The order inside the list is the sort key — kit type, then kit number — so it is grouped by kit type, not by the sequence in which kits were administered.

This is a specification question rather than a bug, but it is the kind that survives to a review table: a reviewer comparing ECREFID with ECLOT sees a one-to-many relationship that the specification may not have intended.

Guardrail. Write the intended cardinality and ordering into the specification, and if one identifier per kit is expected, emit one row per kit instead of collapsing. The verifier prints the collapsed record for a visit carrying 80 kits, which is what makes the mismatch concrete.

F5  The reference list is truncated at 200 characters, mid-number

length refid $200 cuts the accumulated string without warning. The capacity follows from the separator and the width of the number: for kit numbers of n digits, floor(202 / (n + 2)) complete entries survive — 40, 33, 28 and 25 for widths 3 to 6 — and the list is cut inside the next entry in every case, so whatever follows the last complete number must never be read as a kit number.

Guardrail. Size refid from the maximum number of kits a single visit can plausibly carry, and add a self-check next to the concatenation: if length(refid) ge 200 then put "WARNING: refid truncated" scn_num= vis_type=;.

Checked. The verifier builds the concatenation the way the collapse builds it, at each of the four widths, and asserts the counts against the formula.

F6  The visit key is normalised differently on the two sides, and the join fails quietly

The IRT side maps DISCONTINUE by exact equality; the clinical side derives its visit from the CRF folder name and maps anything containing the substring DISCONT. The two agree on DISCONTINUE and on END OF TREATMENT, but not on a value such as DISCONTINUED, which scenario S16 exercises: the clinical side folds it, the IRT side leaves it alone, and the left join then matches nothing. The symptom is a blank ECREFID on those visits and no message anywhere — a left join reports nothing, and the visit simply looks as though no kit was recorded.

Both halves of the mapping are one-line fixes. The risk is structural: as long as the same visit vocabulary is maintained in two places, the two can drift again.

Guardrail. Route both sides through one shared mapping so a single edit changes both, and count the unmatched left joins in QC rather than relying on the log to say something. The verifier tests the two mappings against the same four labels and asserts that DISCONTINUED still misses.

6Reuse checklist

What to change, and what to check before the pattern goes into another program.

  • Parameterise the input and the join key. The IRT table name, the subject variable and the visit variable are the only study-specific parts. Keep them in one place, and route the visit mapping used here and the one used on the clinical side through the same code.
  • Confirm the key types match. A numeric key on one side and a character key on the other gives a walk that probes with the wrong values and finds nothing. This is the failure mode most likely to reach production unnoticed, because a miss is a normal outcome of the loop.
  • Decide the duplicate rule before the first run. If two rows can describe the same kit, encode the rule in a sort column, or use duplicate: "error" — and check that the deduplication upstream leaves the conflict in place for the load to see. A by list that already makes the key unique makes the declaration decorative.
  • Size refid from the data, not from habit. Establish the maximum number of kits a single visit can carry, multiply by the width of a kit number plus two, and add a self-check.
  • Keep a status column and count it. chain_status turns three log-only outcomes into something a QC step can fail on.
  • Keep the diagnostic under a switch. One conditional put per unresolved row stays readable at any size, but the status column is what QC reads: a column is countable, log lines are not.
  • Drop the scratch variables. The hash payload and the pointer live in the PDV and are written out with everything else unless they are dropped deliberately.
  • Re-run the harness after any change to the split, the key definition or the collapse. The expected values are cheap to maintain and the scenarios are the ones that actually break.

7The check that ships with this note

One self-contained SAS program, the dummy data behind every scenario, and what a passing run prints.

7.1 The verifier

kit_chain_check.sas sits at the root of this repository, beside the note. It is Base SAS only — no study macros, no formats, no external libraries, no input files: every row it reads is a datalines line or the output of a loop inside the program itself. It runs the four chain steps over one scenario at a time and asserts what came out.

The step it runs is the step in Listing 1 to Listing 4. That is checked rather than claimed: reference-model/code_fidelity.py compares the verifier's copy against v_ec.sas statement by statement, with comments, case and whitespace ignored, and fails if a single statement of the program is missing. Two additions are expected and named in the file: the split reads the fixture instead of the study extract, and two lines count the probes each row makes, so the probe budget can be asserted rather than assumed.

The shape of the program is worth knowing before reading its output:

PartWhat it does
FixtureOne pipe-separated line per row of the IRT extract, nine fields, for S01–S14 and S17. A . in the last field is a terminal kit.
Expected resultsOne line per visit-level row: the kit, lot, batch, status and probe count the row must resolve to.
Generated casesS15 (volume) is built by a loop; F4 and F5 build their own inputs, because they are about the collapse rather than the walk.
The stepListings 1–4, run once per scenario through %run_case.

7.3 What a passing run prints

Two tables, both from data the program builds. The first is one row per fixture case — the kit, lot, batch, status and probe count that the step produced, next to what was expected, with a verdict column. The rows of S15 are left out of that print unless one of them fails, so the table stays readable at volume.

The second is the assertions, one line each, and it is the part to read after an edit. Besides the per-row comparison it covers the cases that are not about a single row:

AssertionWhat it pins down
S13Zero rows reach the visit-level feed, and the case produces no output row.
S14Four replacement rows enter the deduplication and four keys leave it — the conflict is still there for the load. Under a by list of the key alone the same rows would leave three keys.
S17Three replacement rows enter and two keys leave, under either by list: identical rows are still one event.
S1520,000 visit rows were walked, all of them on the terminal kit, none of them over the probe budget.
F4For a visit carrying 80 kits, the collapsed record keeps the last one as its kit number, and its lot and batch are that kit's.
F5The number of whole kit numbers that fit in refid at each of four widths, against floor(202 / (w + 2)).
F6The two visit mappings agree on three labels and disagree on DISCONTINUED, which is the join miss of S16.

Probes are asserted for every row, which is what distinguishes the two ways a walk can end: S07 and S08 must show exactly 100 probes and a status of UNRESOLVED, so a change that made the loop stop early would fail the check instead of looking like a fix.

7.4 How to run it

sas kit_chain_check.sas            # batch: the log carries the report and the exit code
                                   # interactive: open the file and submit it

A passing run ends the log with one line:

kit chain check: 22 checks, 22 pass, 0 fail

22 is the number of rows the assertion table prints with the fixture as it stands, and the pass count has to equal it: one row for the per-case comparison, and one for each of the structural assertions listed above. A run that reports a smaller number of checks has lost an assertion, not gained a pass.

Two things about the run are deliberate and are worth knowing before the log is read:

  • The last block is expected to fail. S14 does not go through the loop with the others, because loading its conflict is supposed to stop the step. That block is the last thing in the file, it is announced in the log, and it exists so the refusal is observed rather than cited. Set demo_conflict = N to skip it — which is also what to do where a scheduler treats an ERROR in the log as a failed job.
  • The volume case dominates the runtime. 240,000 replacement rows and 20,000 walked rows are nothing for SAS, but they are the slowest part of the check. Lower vol_subjects when the point being checked is not volume.

After any edit to the program, two commands keep this note honest:

python reference-model/code_fidelity.py   # the listings here, and the verifier, against v_ec.sas
python reference-model/ec_chain_verify.py # the same scenarios under a dependency-free emulation

7.5 What it settles, and what it does not

The check is code, not testimony: anything it asserts is settled by running it. Three behaviours were previously assumed rather than observed, because no SAS session was available where this note was written, and they are exactly what the run answers:

  1. That a load declared duplicate: "error" ends the step with an error and produces no output data set, rather than warning and emitting a partial table. Findings F3 and scenario S14 rest on this.
  2. That a zero-row table can be loaded through the dataset: tag, which is how S10 reaches its dangling pointer. The verifier runs that case, so the log answers it either way.
  3. That the while test of do i = 1 to 100 while (…) is evaluated before the first iteration as well as before the rest. That is why S01 and S09 — rows whose pointer is already missing — must show zero probes.

What it does not settle is what no program of this size can: whether the fixture is the whole of the shape the real IRT extract can take. The scenarios were chosen from the ways a replacement chain breaks — an absent kit, a cycle, a conflict, a duplicate, a volume case — and a new shape of bad input means a new fixture line, not a re-reading of this note. The expected results are part of the check for the same reason: they are the specification of the step, written down where a change has to face them.

The emulation in reference-model/ec_chain_verify.py stays in the repository because it does one thing the SAS check cannot: it re-runs the same scenarios under the key-only by list and prints the two different answers that result, which is the measurement behind §5.4. It is standard-library Python 3 with no dependencies, and it shares the fixture with the SAS check.

The listings in §3 are v_ec.sas as it stands, not a paraphrase of it, and that is checked rather than claimed: reference-model/code_fidelity.py compares every statement of the listings, and of the step that kit_chain_check.sas runs, against the program. The check itself is a single self-contained Base SAS program — 17 scenarios, one assertion per case, no study macros and no external input — and the dummy data behind every case is printed in §7.2. SAS was not available in the environment where this note was written, so the expected results in §7 are the specification the check asserts rather than a log that was read; §7.5 lists the three behaviours that the run settles. All data is synthetic: study identifiers are placeholders, no subject-level information is present, and the IRT extract is referred to by a generic name.
